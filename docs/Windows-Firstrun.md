# Первый запуск на Windows

Двигок ни разу не запускался на Windows. Компилируется — да, `windows-2022`
есть в матрице CI вместе с рендерером и `dbghelp`. Запускался — нет. Этот
документ про то, как сделать первую попытку так, чтобы из неё вышел ответ, а не
«не работает».

Цель первого шага — **дойти до главного меню**. Не кампания. Меню проверяет
почти всё, что мы поменяли: шрифты из SDF, два 2D-пространства, полосы по краям,
консоль, загрузку шейдерного пака. Карта не проверяет ничего из этого и добавляет
десяток своих причин упасть.

## Что собрать в папку

Рядом с exe должно лежать вот это. Порядок важен только в том смысле, что без
первых двух пунктов движок не стартует вообще.

```
jkx_ja.exe                 из build\Release\
jkx_ja.pdb                        "         (символы, см. ниже)
jagamex86_64.dll           из build\Release\  (игровой код)
SDL2.dll                   из vcpkg, x64-windows\bin
base\shaders.pak           из build\Release\base\
base\fonts\*.jkxfont       из build\Release\base\fonts\
base\fonts\*.png                  "
base\assets0.pk3 ... assets3.pk3  из ретейл-установки Jedi Academy
```

**`base\fonts\` — это восемь файлов, а не один каталог рядом с паком.** Если
скопировать только `shaders.pak`, движок поднимется и меню будет кликаться, но
текста не будет нигде. Он про это скажет (`RE_RegisterFont`), но сообщение легко
пропустить среди прочего.

**`.pdb` кладётся рядом с exe.** Без него отчёт о падении содержит только
адреса: рендерер слинкован в движок и экспортирует ровно один символ, поэтому
каждый кадр стека выглядит как `GetRefAPI+0x4fc9` и не значит ничего. С ним
`vk_crash.cpp` печатает функцию и строку. Release собирается с `/Zi`, так что
`.pdb` есть и в релизной сборке, и он лежит в том же артефакте CI.

**`base\` берётся из `build\Release\base\`, а не из `build\base\`.** Visual
Studio — многоконфигурационный генератор: он кладёт бинарники в подпапку по
конфигурации, а `CMAKE_RUNTIME_OUTPUT_DIRECTORY` указывает на родителя. До
правки в этом же коммите генерируемые данные ложились на уровень выше exe, где
движок их не ищет. На Ninja и Makefile подпапки нет и разницы не было — поэтому
никто и не замечал: Windows-сборку никто не запускал.

Артефакт CI (`jkx-Windows`) теперь содержит и `base\**`.

## Чем запускать

```
jkx_ja.exe +set fs_homepath . +set com_logfile 2 +set developer 1
```

- `fs_homepath .` — чтобы лог и конфиг легли рядом с exe, а не в
  `Documents\My Games\OpenJK`, и их было легко найти.
- `com_logfile 2` — писать `base\qconsole.log` с флашем после каждой строки.
  Без этого лога нет вообще, а без флаша нет последней строки перед падением —
  то есть ровно той, которая нужна.
- `developer 1` — подробности загрузки.

## Где искать файлы после запуска

Три файла, и лежат они в трёх разных местах — это стоит знать заранее, потому
что искать их не там очень легко.

| файл | где | чем управляется |
|---|---|---|
| `qconsole.log` | `<fs_homepath>\base\` | пишется только при `com_logfile 1` или `2`. **По умолчанию `fs_homepath` — это `Documents\My Games\OpenJK`, а не каталог с exe.** С `+set fs_homepath .` ляжет в `GameData\base\` |
| `jkx_crash.txt` | **рядом с exe**, всегда | путь берётся из `GetModuleFileName`, не из файловой системы движка (`vk_crash.cpp:228`) — поэтому он появляется даже при падении до инициализации FS |
| `openjk_sp.cfg` | `<fs_homepath>\base\` | конфиг движка. Ретейловые `jaconfig.cfg` и `jampconfig.cfg` — не наши, мы их не читаем и не пишем |

`com_logfile 2` пишет с флашем после каждой строки: медленнее, но последняя
строка перед падением тоже попадает в файл. Для отладки нужен именно он.

## На что смотреть

**Хорошо, если в логе есть:**

```
renderer: rd-vulkan, built in
selected physical device: 0
VK_RENDERER: <имя видеокарты>
selected presentation mode:
--- Common Initialization Complete ---
```

и в меню читаемый текст.

**Плохо, и что это значит:**

| в логе | это |
|---|---|
| `shaders.pak is missing` | не скопировали `base\shaders.pak`, либо взяли из `build\base\` вместо `build\Release\base\` |
| `font ocr_a is missing and there is no other font loaded` | нет `base\fonts\` |
| `font aurabesh is missing, so alien text will be drawn in a Latin face` | ожидаемо и не ошибка. `aurabesh` не генерируется из TrueType, команда для сборки из своих ассетов — в сообщении |
| `Couldn't load default.cfg` | нет ретейловых pk3 в `base\` |
| текст есть, но серая размазня | атлас не тот: должен грузиться `fonts\<имя>.png`, а не ретейловый `.tga`. Мы регистрируем шейдер с расширением именно поэтому — если это всё же случилось, значит порядок поиска в файловой системе ещё хитрее, и это находка |
| окно есть, всё чёрное, лог обрывается на `----- R_Init -----` | Vulkan не поднялся. Дальше — `vid_restart` не поможет, нужен лог целиком |
| `SDL_Vulkan_LoadLibrary` | SDL2.dll собран без Vulkan. Тот самый случай, ради которого в CI стоит проверка `SDL_VIDEO_VULKAN` |

## Что заведомо будет не так

Это не ошибки, это известные места, чтобы не тратить на них время:

- **Инопланетные надписи латиницей.** `aurabesh` не собран — см. выше.
- **Меню другой гарнитурой и с другой развёрсткой.** Так и задумано: Libre
  Franklin с собственными метриками, текст перетекает. Пункты, стоявшие впритык,
  могут вылезти за свои рамки — это и есть то, что надо увидеть глазами
  (`docs/Backlog.md`, §1.2).
- **Чёрные полосы по бокам, если монитор шире 4:3.** Интерфейс вписывается, а не
  растягивается. На 16:9 полосы будут заметные, потому что контент пока
  авторен в 4:3.
- **Правая половина HUD** прижимается к краю экрана — но HUD в меню не виден,
  это уже второй шаг.

## Второй шаг, если меню поднялось

Из консоли, **не** «Новая игра». Карта зависит от игры — это ровно те же две
строки, которые «Новая игра» выполняет за тебя (`code/ui/ui_main.cpp:1062`):

```
\map yavin1        для jkx_ja  (Jedi Academy)
\map kejim_post    для jkx_jo  (Jedi Outcast)
```

`kejim_post` в установке Academy нет, и движок про это скажет честно:
`can't find maps/kejim_post.bsp`.

Карта проверяет то, чего меню не касается совсем: загрузку BSP, лайтмапы,
Ghoul2-модели, ICARUS. И там впервые исполнится путь, который здесь не
исполнялся никогда: на настоящей видеокарте `maxBoundDescriptorSets` будет 32, а
не 8, и включится PBR-ветка, которую lavapipe отключает.

Если карта загрузилась и рисует кадр — дальше вопрос игровой логики, а не
движка, и кампанию можно запускать обычным способом.

## Если вылетело на карте

Первое, что делится пополам, — путь освещения:

```
jkx_ja.exe +set fs_homepath . +set com_logfile 2 +set r_normalMapping 0 +set r_specularMapping 0
```

Оба нуля принудительно включают `useFastLight` (`vk_init.cpp:604`) — тот путь,
который гоняется в headless-тестах на lavapipe. PBR-ветка на этом железе
исполняется впервые в истории проекта, и это самый вероятный подозреваемый.
В логе строка `JKX: lighting path = ...` прямо говорит, какая ветка выбрана.

Если с этими флагами карта грузится — виноват PBR. Если вылетает одинаково —
рендер ни при чём, и дальше по логу: BSP, Ghoul2 или ICARUS.

`jkx_crash.txt` рядом с exe нужен вместе с логом, но только если рядом лежит
`.pdb`: без него в отчёте одни адреса.
